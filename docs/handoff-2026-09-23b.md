## 2. The drive: method, and what it found

Method (first-class, and reusable): **drive the box as the operator.**
`python ~/bin/mm_say.py --to bot-a --file <order.txt>` posts as @david and announces the real sender;
the bot's own log (`\\a LAN address\C$\tinycmdr\tinycmdr.log`) and its event journal
(`sessions/mm-<id>.events.jsonl`) are readable over SMB, so every answer is
graded against the tree and against the tool calls that actually ran.

```
WO1  three probes: what is NOT in your tool list; every atomic_write_text call site with line
     numbers; the fuzzy-anchor tool + a real edit.
WO2  the same call-site question; config.json vs config.example.json; a background job reported
     without blocking.
WO3  a multi-file content search; a write whose payload matches a confirm pattern; a fresh-eyes
     sub-agent re-check of WO2's answer.
WO4  the multi-file search again; re-check the sub-agent's claims yourself and say which; quote
     the last web_search result.
```

## 3. The toolsmith (the operator's public-release note, now built)

He flagged it mid-session: **the public shapes ship no tools at all**, and the piece he cares about
most is a tool that lets the harness/model know how to make a tool, or at least import one and
index it. That is `tools/toolsmith.py` (native shape, stdlib only, committed b3536b2):

```
new    scaffold a native tool from a short arg spec ('path:str=., top:int=5, human:bool=True')
wrap   import ANY existing script as a manifest tool (command + schema on stdin/stdout)
list   index tools/ by shape, with the NAMES each file registers
check  run the HARNESS's own loader (load_tool_defs - the single reader create_tool and the write
       verifier use) and report its verdict; "OK" is the loader's judgement, not this tool's
```
Packaging lockstep done: `.gitignore` carve-out, `build-package.py` SHIP + APP_FILES,
`build-cli-package.py`'s tools folder; the installers copy `tools/` wholesale so they need nothing.
`tests/test_toolsmith.py` is 28 checks on both builds, and the check caught two real bugs while it
was being built (a JSON `true` written into a Python scaffold - pprint now; a quoted interpreter
path PowerShell mangled into "no verdict" - an argv list now).

## 6. Traps this session paid for

```
- An f-string prompt edit needs DOUBLED braces: `search_files {pattern, path}` inside the
  build_system_prompt f-string evaluated `pattern` and the whole prompt raised NameError. The suite
  caught it; add the field with {{ }} and re-measure the prompt.
- The operator's proxy (me) answering a confirm needs `mm_say --no-announce`: with the announce line
  first, the answer's first word is "[hermes," and the parser reads that as a NO.
- MSYS paths do not work in NATIVE python: open("/c/Users/...") raises, and a poll loop that caught
  the exception looked like "the bot announced nothing" while four hosts had. Use C:/... paths.
- A trap question (about a call that never ran) inside a 3-probe order can eat the whole run: the
  other two probes finished in minutes and the third burned twenty.
- A subprocess with a quoted interpreter path: pass an argv LIST, never one shell string
  (`"C:\...\python.exe" "C:\...\x.py"` came back as "Unexpected token" on PowerShell).
- A Python scaffold needs a PYTHON literal: json.dumps writes `true`/`false`, which is a NameError
  inside a .py file. pprint.pformat for anything embedded in a Python source file.
- The drive's own log line is the ground truth for "did the hint fire": a hint that only rides a
  tool RESULT is invisible to every later reader.
```
